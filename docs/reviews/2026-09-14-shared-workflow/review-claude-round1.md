# Adversarial review — DataCraft autonomy implementation (review surface frozen 2026-09-14)

## Summary

I verified the frozen surface against files.json (38 files, all SHA256 match both the copies and the live sources), read all seven runtime scripts in full, the PM/design/ui-test diffs, the library skill docs, the new test suites, and the generated Codex packages, and cross-checked the executable contracts against the docs. The core runtime is solid: four-attempt accounting holds across restart/collision/internal-retry/recovery (confirmed by behavioral subprocess tests that drive the real loop against a fake Ringer, not mirrors of the implementation); refunds are exact-zero-attempt, once-per-reservation, and bound to the authoritative record; crash residue is monotonic (`claim_shaped` rejects erased reservations, replenished counters, and altered refunds); recovery holds both RepoLock and the seam lock for its whole transaction; the pause CLI acknowledges during a worker, drains the wave and integration, and never dispatches after acknowledgement; legacy invocations are preserved and cannot bypass a persisted budget. I also closed one suspicion with independent evidence: the strict run-record reader requires 0600 perms and `run_id == filename stem`, and real Ringer records on this machine (all since 2026-08-29, including the 2026-09-14 implementation run) satisfy every strict-reader requirement, so the fixture's `chmod(0o600)` is not papering over a real mismatch.

Three findings survived verification, ranked below. Limits: I did not run a live opted-in loop against real Ringer (record compatibility was verified against existing on-disk records, not a fresh strict-mode run); the UI pilot denial stands, so no claim here about actual GUI behavior; LLM-behavioral properties of the skill prose (grilling, session skills) were checked for internal consistency only.

Finding: The ship-acceptance validator silently reverts to legacy single-evidence mode on Execution-agreement heading variants that the runtime fails closed on, dropping all evidence-channel enforcement for an approved-autonomy intent.
Evidence: `plugins/pm/scripts/acceptance.py:31` — `fenced_json` matches only `^## Execution agreement\s*$` (case-sensitive, no trailing text), returning `None` (= legacy intent) for any variant. `library/.../build-swarm/scripts/agreement.py:91-93` matches `^##\s+Execution agreement[^\n]*$` case-insensitively and then rejects any non-exact heading. Reproduced with the frozen copies: for `## Execution agreement — approved 2026-09-14` and `## Execution Agreement` (each containing a fully valid, approved dc-autonomy-v1 block), `acceptance.fenced_json` returns None while `agreement.load` raises "expected exactly one ## Execution agreement heading". With `agreement is None`, `acceptance.py:144-153` skips the "adopted intent requires `## Evidence requirements`" gate and `verdict()` never enforces channels — a record with no `ui`/`state` evidence returns `shipped`.
Impact: An intent whose approved agreement heading was hand-embellished (a date, a capital A — plausible human edits to a markdown doc) gets the strong runtime refusal on the build side but a silently *weaker* ship gate: code-complete work can be validated `shipped` with no UI interaction, no persistence read, and no channel identity checks. This directly contradicts the shipped contract in `pm/WORKFLOW.md` ("ambiguous agreement does not grant the new autonomy *and* does not silently fall back to legacy permission") and SDLC.md's fail-closed gate rule, and it is exactly the "omit mandatory channels" failure the workflow was built to prevent.
Fix: In `fenced_json` (or a wrapper for the 'Execution agreement' heading specifically), detect near-miss headings the way `agreement.py` does — search case-insensitively with trailing text allowed, and if a match exists that is not exactly `## Execution agreement`, raise (→ blocked with a reason) instead of returning None. Add a CLI test with a decorated heading asserting exit 2.

Finding: A pause request acknowledged between the wave's last pending-check and Ringer dispatch permanently consumes the wave's attempt reservations with no refund and no recovery path, so a paused-and-resumed run can exhaust a ticket's entire 4-attempt budget without any worker ever running.
Evidence: `library/.../build-swarm/scripts/loop.py` — the pre-wave pause check runs at line 1207; reservations are then taken and committed at lines 1242-1249; the next pause gate is inside `ringer()`'s dispatch critical section (lines 675-683), which raises `PauseBeforeDispatch`. The handler (lines 1257-1263) releases claims but keeps the reservations ("pause before dispatch; reservations conservatively retained"). The window between line 1207 and dispatch includes `ringer lint` (subprocess, up to 120s) plus the claim commit, and the control monitor acknowledges a request within ~100ms, so a user pause landing in that window burns `min(2, remaining)` attempts per wave ticket. No refund is possible (`budget.refund` requires a completed Ringer record; no run happened), and after budget exhaustion the ticket is parked at line 1178-1180 with *no failure record*, so `recovery.py` refuses (`budget.recover` requires a diagnosed `behavior`/`conflicting-work` failure). Two unluckily timed pauses on the same ticket leave it permanently undispatachable; the only way out is hand-editing the validated `**Autonomy:**` header. The test suite covers pause during worker and during integration but has no test for a pause acknowledged in the claim→dispatch window.
Impact: The user-facing "graceful pause" feature silently costs real budget when used at the wrong moment, and the loss is invisible (commit message only) and irreversible through any provided CLI — a ticket can reach "worker attempt budget exhausted; no dispatch" having never run a worker, on a run whose terminal state truthfully says `paused`.
Fix: Take the reservations inside the same control-lock critical section that gates dispatch (i.e., check `dispatch()` first, then reserve+commit, then Popen without releasing the control lock between reserve and launch), so an acknowledged pause is seen *before* any grant is written; alternatively, on `PauseBeforeDispatch` record an explicit pause-refund entry (a distinct refund kind carrying the pause acknowledgement, since no dispatch provably occurred — the loop itself is the authority that nothing was launched). Add a test that requests pause during a slowed `ringer lint` and asserts `used` is unchanged after the pause.

Finding: acceptance.py's "malformed agreements fail closed" claim is enforced only for `policy` and the `approved` type; a structurally invalid approved agreement (missing scope/actions/build, out-of-bounds limits) passes ship validation, diverging from the documented fail-closed contract and from the runtime parser.
Evidence: `plugins/pm/scripts/acceptance.py:144-149` checks only `agreement.get('policy') != 'dc-autonomy-v1'` and `isinstance(agreement.get('approved'), bool)`. The project's own test constant demonstrates the gap: `tests/test_pm_evidence_channels.py` `AGREEMENT` uses `"actions": ["local-edit", "local-test"]` — an agreement `agreement.py:47-48` rejects outright (requires local-edit/local-test/local-commit/ringer-build) — and the CLI test expects it to ship. An approved block like `{"policy":"dc-autonomy-v1","approved":true}` with no scope, actions, or build also passes acceptance validation (with an Evidence-requirements block present). `pm/WORKFLOW.md` ("Fail closed. An unknown policy, malformed JSON, duplicate block, or ambiguous agreement…") and the code comment at acceptance.py:145 both promise more than the check performs.
Impact: The ship gate certifies records for intents whose agreement the runtime would refuse, so the two components disagree about whether the same intent is valid; the practical harm is bounded (the ship validator's channel enforcement still runs when the heading is exact, and the build runtime independently refuses), but the docs' single fail-closed story is not true at this seam, and a malformed-but-approved agreement can reach `shipped` without anyone being told the agreement is broken. Note the actions divergence may be partly intentional (review-only agreements legitimately omit build actions — cross-review-gate's reference shows one), which argues for validating shape/bounds, not the runtime's required-actions set.
Fix: In acceptance.py, validate the approved agreement's structural shape before trusting it: nonempty string `scope`, `actions` a list of known action names, `build` (when present) integer bounds max_worker_attempts 1-4 / recovery_cycles 0-1 / max_tasks 1-3 — blocking with a named reason on violation; or, if the ship gate is deliberately narrower, correct the acceptance.py comment and the WORKFLOW.md/ship-acceptance wording to say which component enforces which part.

Confidence: high

pm 0.21.0 · how Joe works now · 2026-09-20

One session per outcome. Siblings when the work is independent.

What this is for: one page to check the workflow against, and to hand a new session when it asks "how do we work here?"
Good looks like: tickets accepted at the same quality, with usage back near the pre-orchestration weeks.
What it is not: a new system. Same skills, same tracker, same Ringer. One new skill, one changed default.

What changed today

The old loop is the default again. whats-next → do the work in that session → stepping-away, which now offers to open a fresh session for the next ready work.

Sibling sessions are how work runs in parallel. Two or three independent tickets, each in its own ordinary session, each through its own merge. Nobody watches the others.

orchestrate is opt-in. A real batch of independent, meaty tickets while you're away. It keeps the stricter rules from pm-021.

Dotted lines are the only contact between sessions. After launch there is none: no polling, no reports, no sweep, no shared board.

The screen: all of these, or it's a no

  • At least two ready tickets that are real outcomes. Small fixes stay serial in one session.
  • Disjoint files, including lockfiles, generated code, migrations, schema and config registries.
  • At most one database writer. No shared port, dev server or browser profile.
  • No ticket needs another's output.
  • The machine has room: memory and CPU checked. Three builds at once ran the 16 GB Mac out of memory on 09-14.
  • You're around to answer each window. One lane sat four hours on a question nobody saw.

The skill answers out loud, yes or no, with the reason. On a no it names the alternative: serial in this session, or orchestrate if you'll be away.

What a sibling is told

Repo: <main checkout path>. You are one of <N> sibling sessions; the others are
working <ticket ids>, leave those alone.
Run whats-next bound to ticket <id>: <title>. Do not pick other work.
Work in your own worktree on branch <name>. Set the worktree up from
docs/agents/worker-env.md if the repo has one.
You own this ticket through its merge: rebase on <base branch>, get green on the
rebased tree, then merge only when the user says so. Close with stepping-away.
Do not message or wait on the other sessions.
Handoff: <this session's file>.

The merge rule

  1. First sibling ready merges first.
  2. Later ones rebase onto it and rerun the checks on the rebased tree.
  3. A conflict belongs to the sibling that hit it, in its own window.
  4. Merge only on your word. Push, deploy and client messages keep their own permission.

Known catch

A fresh worktree doesn't have uncommitted work or anything git ignores: env files, dependencies, local databases, and _pm/ in repos that ignore it. Commit what a sibling needs before launching, and say in the prompt what it must set up. A launched session shows as created and pending until you click it.

Why it changed

Orchestration doubled the calls, not the context.

Claude Code only, from the local session logs. Context per call held at 238K, 190K, 234K.

Over 09-14 to 09-16 the lane sessions each cost what a normal session costs, 30 to 120M. The orchestrator session watching them was 628M of 1,924M. Sibling sessions keep the lanes and drop the watcher.

Still unmeasured: tokens per accepted ticket. That number, not the weekly total, says whether any parallel mode is worth it. Every orchestrated run now records tickets accepted and tokens used.

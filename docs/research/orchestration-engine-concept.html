Concept · parked on purpose · 2026-09-20

Move the orchestration loop out of the model's head.

What this is for: so "let's talk about the engine build" starts with the thinking already done.
Good looks like: more accepted tickets per week of plan allowance, with Joe away, on any host: Claude Code, Codex, Cursor. At the same quality. Less intervention that produces garbage is a loss, so quality is the gate on every rung below, ahead of tokens.
What it is not: a new tool, a Hermes replacement, or anything Claude-only. Nothing here is built.

The pushback, first

Good idea. Don't build it. Maybe not ever.

The cost problem this solves had one cause: the Marvel run started inside a day-old session already holding 327K tokens. A fresh session fixes that for free, and pm 0.21 now requires it. That fix hasn't been run once yet.

Most of the engine also already exists. build-swarm's loop.py is this loop, in code, over Ringer, and it has never run on a real repo. Building a layer on top of a loop you haven't used is the pattern you asked me to call out: dc-loop (parked as too big), the Hermes pilots, build-swarm, and now this, in under four weeks.

Your own logs agree. The week orchestration started, Claude Code usage went from about 1.0 to 1.2 billion tokens a week to 2.5 billion. Context per call didn't move (238K, 190K, 234K). Calls doubled, 5,200 to 10,900. Orchestration costs more because it is more model calls at once, and an engine shrinks context per call, which isn't what grew. What nobody has measured is tokens per accepted ticket. That number decides this, not the weekly total.

Flip condition: two fresh-session runs where the lead seat still out-spends its workers, and you are actually hitting the weekly limit. Until both are true, this page is a parking spot.

The problem, measured

The orchestrator re-reads itself on every call.

A model has no memory. Each call resends the whole conversation. An orchestrator that lives in one long conversation pays for that conversation on every step, whatever model it is.

Tokens, cache reads included. Marvel: 125 calls at about 436K each (327K at the first call, 532K at the last). Hermes: 311 calls at about 236K. The last bar is arithmetic, not a measurement: the same 125 calls at a 120K average. That bar is the whole argument for trying the free fix first.

Hermes can cap its context with one setting. A Claude Code or Codex session mostly can't. Code has no context at all, and state on disk costs nothing to keep. That is the engine idea.

Engine: the loop is code, the model is a guest

flowchart LR
    S[Session] -->|accepted brief| P[Prep step]
    P -->|committed checks, Owns| L[loop.py]
    L <--> R[Ringer workers]

    V -->|findings become ticket states| L
    L -->|run records| T[Report step]
    T --> S
    L <--> D[(Disk)]

Each step is a fresh call with a small packet. No step keeps a conversation. Nothing a model writes decides what runs next except through a ticket.

The three new steps

Everything else stays deterministic.

1. Prep

One Ringer task per ticket, run as a wave before the build wave. It writes the ticket's check, proves it red, and proposes the owned files.

Replaces
The session scouting and writing acceptance tests: 16 minutes and most of the context in Marvel.
Packet
The ticket, the intent's constraints, the few interface files a cheap scout names.
Risk
The big one. Marvel's tests were the best thing in that run, and they were written with the whole repo in mind. A thin packet may produce weak or vacuous checks, and then everything downstream is confidently wrong.

2. Review

One bounded read of the integrated diff per wave, conditional like pm's review schedule. Not a panel after every green.

Replaces
The session reading each patch. Or, with loop.py today, nobody reading it until the gate.
Packet
Intent, diff, check evidence, one question.
Risk
It spends back some of the tokens the engine saved. Marvel's README passed its check with three wrong statements; only a read caught them, so this step can't be dropped.

3. Report

One call over the run records at the end. Shipped, what each check proved, not verified, waiting on Joe, seat usage.

Replaces
The session writing the report from a full context: 20.5M more tokens in Marvel.
Packet
Run records, ticket states, commits.
Risk
Low. Mostly templating.

The return is tokens on a plan allowance, not dollars. It only matters if the limit is what stops you. After the Marvel run the weekly Fable meter read 24% with five days left. The Codex week in the Hermes pilot did run out, on a 900K window that has since been capped and not re-tested.

Honest read: the Marvel run shipped eight tickets in fifty minutes, all first try. The process works. What's unproven is whether it's too expensive once the free fix is in.

The path, cheapest first

Three free rungs before any build.

  1. Run pm 0.21 as written. Next orchestrated job: fresh session from a written brief, Ringer output read by path, seat usage in the report.

    Stop here if lead-seat tokens come in at or below the workers'. The engine stays parked.

  2. Use the loop you already have. Prepare three real tickets by hand and run loop.py --wave 1 on an integration branch. This is build-swarm's own overdue proving run.

    Stop here if the session's share is now small enough. Then the lesson is "prepare tickets and use build-swarm", and nothing new gets built.

  3. Prove prep by hand. Same three tickets, but prep runs as plain Ringer tasks with hand-built packets. Compare the checks they write against the ones you'd have written.

    Stop here if the checks are weaker, or the whole thing isn't at least three times cheaper at the same first-try rate.

  4. Only now, build. Packet builder plus three task templates, inside build-swarm. Read dc-loop's ADR 0006 first so the same weight isn't rebuilt.

    Size it as three manifest templates and one script. If the plan grows past that, that is the signal to stop.

Open questions for the build conversation

What we don't know yet.

  • Does prep quality survive a small packet? Rung 3 answers it. Everything hangs on this.
  • Who picks the interface files for a packet: a cheap model, or grep rules?
  • One prep task per ticket, or one per brief so shared fixtures agree?
  • How does a session start a run and watch it without holding its output? Likely: start detached, read control.py status, read the final report.
  • Why exactly was dc-loop parked? Its ADR 0006 isn't on this Mac and wasn't read for this sketch.
  • Claude Code's Projects beta has the same shape (one coordinator, a cloud thread per task, the coordinator sees reports only). It is Claude-only, cloud-only and has no executed checks, so it doesn't replace this. If the contract stays brief → tickets with checks → reports, it could later be one more lane.

# Runway app

Menu bar app for Runway. Swift package, no Xcode project. One third-party dependency: [SwiftTerm](https://github.com/migueldeicaza/SwiftTerm) (MIT, pinned to exactly 1.20.0), whose terminal view runs the Claude sessions in the window's pane (see "Terminal pane" below). macOS 14+.

- `RunwayCore`: models, file parsing, state logic and command builders, no SwiftUI. Unit tested.
  - `RunState.swift`: heartbeat + launchctl + pause file + decisions waiting → per-project and overall state. A heartbeat in an active phase whose pid is gone is an error, not running.
  - `Commands.swift`: Start = `schedule.sh install <repo> <minutes>`, Stop = `schedule.sh uninstall <repo>`, Run now = `launchctl kickstart gui/<uid>/<label>`, Pause/Resume = `runway.py pause|resume`. A failed command shows its stderr at the top of the menu.
- `RunwayBar`: SwiftUI `MenuBarExtra` app. Icon follows the overall state (airplane running, bell waiting on you, pause, moon all off, triangle error) with a count of decisions waiting. One submenu per project; Pause all loops / Resume; Scripts.

Notifications (`Notifications.swift` in RunwayCore, delivery in `RunwayBar/Notifier.swift`): once per decision packet, once per ticket parked after a failed retry, and once per project with ready tickets but its loop off (repeat at most every 4 hours, never in quiet hours from `~/.runway/machine.json`). What was notified is remembered in `~/Library/Application Support/Runway/notified.json`, so a restart doesn't repeat it; a ticket that is answered and later parked again notifies again. The icon turns amber for ready-work-while-off whether or not notifications are allowed. Notifications need the bundled app (`make-app.sh`). A click records the tab to open (`ProjectStore.requestedRoute`); the app has no window yet, so nothing shows it.

Window (`RunwayBar/RunwayWindow.swift`, opened from the menu's "Open Runway window"): project sidebar with state dots and decision badges, a title bar with the state pill, interval, Start/Stop and Run a tick now (the menu's actions), and two tabs, Board and Runs. Spec: `docs/specs/runway-board.md`.

Board (`RunwayCore/Board.swift`, `RunwayBar/BoardView.swift`): a strip of numbers (merged this round, spend and tokens today, needs you, next tick), then five columns built by `Board.build` from `status --json` and `_pm/runway-runs.jsonl`: **Blocked** (the `blocked` group, "Waits on …"), **Needs you** (the `waiting` group, then errored tickets that aren't running or done), **Up next** (`ready_auto` then `ready_prep`, queue order; prep tickets are tagged), **Running** (the `running` group plus the heartbeat's live ticket) and **Done this round** (tickets with a `done` outcome since the last `finish` row, with their minutes and cost, `RoundLog.merged`). Each ticket sits in one column. Running is a big card with the elapsed clock, attempt, harness, the sync→merge phase strip and the last three log events; with the loop off it says how many tickets are ready and offers Start. Clicking a card opens a details pane on the right (a second click or the close button shuts it): the title, why it's where it is, the packet with a note field and Go / No when it waits on Joe (the same `runway go|no` through `DecisionsFeed`, only from those buttons, and "Answered" after), **Talk it through** for waiting, errored, running and done tickets (a done ticket's session answers questions about what got done and posts nothing), **Resume worker** when status marks the ticket `resumable` (a done one too: the engine recreates the worktree from the kept branch), the tracker link, and the ticket's prep / agent / check / outcome rows from the runs log (`RoundLog.history`). There's no drag and drop: a move would be a tracker change, and a go only lands when Joe presses Go or types it. Under Done this round, **Open last review** (when status says `review_resumable`) runs `discuss --review`, the last finish review's own session, in the pane or Terminal. Status is fetched every minute (it calls the tracker), the runs log every 10 seconds, the log every second. The activity log is a drawer under the board: closed it shows the latest event on one line, open it shows the full list (open or closed is remembered). The Now math (`NowMath`) and the log reader (`LogTail`, which reads only appended bytes and starts from the last 64 KB of a big file) live in `RunwayCore/NowTab.swift`. A project in error (a dead heartbeat, a non-zero last exit, an unreadable plist) puts its error at the top of the board: the `ProjectStatus` detail in full (for example "stale heartbeat (pid 123 not running)" or "last tick exit 1"), the last six log lines, and a **Talk it through** button that runs `discuss --loop`. Every route into the window (the sidebar, the side panel's red card or Details, the menu, a notification) opens the board, with that ticket's details open when the route names one.

Errors and the **Talk it through** button (`RunwayCore/Errored.swift`): a ticket whose `errored` field is set in `status --json` (the kind of its latest attempt that didn't merge; a missing field means not errored, so an older engine still works) gets a red flag with the kind in words ("check failed", "merge conflict", "agent failed", "no commits", "signed out"). It shows in the side panel's Needs you section (errored tickets follow the waiting ones), on its board card and in its details pane, in the menu bar dropdown (an "Errored tickets" list under the waiting decisions) and on the Runs tab rows for that ticket. The icon's count includes errored tickets. The button shows for every waiting ticket (a packet card or a parked one), every errored ticket and every project in error, and for no others. It runs `osascript` to tell Terminal to activate and run `cd '<repo>' && python3 '<runway.py>' discuss '<ticket id>'` (or `discuss --loop`), each part shell-quoted; the engine owns the brief and the prompt, the app only opens the session. Go and No are unchanged: the session posts its answer with `runway go|no` and the next status refresh shows it. A failed launch shows its output beside the button, like a failed Go. Notifications for a decision or a parked ticket carry a "Talk it through" action; a plain click opens the board on that ticket.

`schedule.sh` and `runway.py` are found from the Scripts setting (a dc-dev-plugins checkout), else from the `runway.py` path in the LaunchAgent plists. The script path is remembered, so a stopped loop keeps its row and can be started again. Decisions waiting come from `runway.py status --json`, polled at most once a minute. "Until tomorrow 08:00" means the next 08:00, so before 08:00 it ends this morning.

Runs tab (`RunwayCore/RunsTab.swift`, `RunwayBar/RunsTabView.swift`): `_pm/runway-runs.jsonl` as a table, newest first (when, ticket, kind, harness, attempt, result, minutes, tokens = input+output, cost) with a totals footer summed from the same rows. Result: an agent call passes on exit 0, `finish` on `check_exit` 0, `outcome` reads `done` as pass and `needs-human`/`stopped` as park. Missing fields show "—" and bad lines are skipped. Session reveals `~/.claude/projects/*/<session_id>.jsonl` in Finder. "Write retro prompt" runs `runway retro` and opens `_pm/runway-retro-prompt.md`. `_pm/runway-pr.md`, when present, shows under "Finish". The log is parsed off the main actor and re-read every 10 seconds.

Decisions (`RunwayCore/DecisionsTab.swift`): `PacketMarkdown` breaks a packet into blocks (headings, lists, code; inline bold and links via `AttributedString`; lines saying "recommend…" get a badge), drawn by `PacketView` in the board's details pane. `DecisionsFeed` holds the board's status and runs `runway go|no <ticket> "<note>"` as Joe (Joe confirmed 2026-10-07 that a Go click counts as his go; it posts his comment to the tracker), once per ticket and only from a Go or No button; then status refreshes and the pane says "Answered: go “note”, picked up on the next tick". A failure shows the command output and records no answer. The menu bar dropdown lists waiting decisions and errored tickets; each opens the board on that ticket.

Side panel (`RunwayBar/SidePanel.swift`): a narrow window beside other work. Each project with tickets in the `waiting` group of `status --json` gets a **Needs you** section above Up next (`RunwayCore/NeedsYou.swift` builds the rows in queue order). A row shows the ticket id and title, why it waits (`reason` when status has one, else `waiting_on`), the packet's recommended option when it marks one, **Open** (the ticket in its tracker), **Details** (the window's board with that ticket's details open) and an **Answer** disclosure with a note field and Go / No, which run the same `runway go|no` through `DecisionsFeed` as the board's details pane and show "Answered" the same way. The bell in the project header scrolls to that section and briefly highlights it, on a single click; with nothing waiting there is no section and no bell. Tickets whose latest attempt errored join the section under the waiting ones with the red flag and **Talk it through** on their rows (they have no Go / No, since nothing waits on an answer; Details opens the board on it too); a waiting ticket gets the button too, and the bell count includes both. A project in error shows a red card with its detail, a click on it opens the window's board, and the button runs `discuss --loop`.

Set up a loop sheet (`RunwayCore/Setup.swift`, `RunwayBar/SetupSheetView.swift`), from "Set up a loop…" at the bottom of the sidebar. It checks this Mac (`SetupChecks`: Python 3.9+, git, `claude --version`, optional `codex` / `cursor-agent`, the engine checkout, the `runway-linear` keychain item) through a login shell, so the PATH matches what the loop sees. Sign-in can't be checked silently, so "Open Terminal to sign in" opens Terminal running `claude`. A missing engine offers "Clone…" (dc-dev-plugins into a folder you pick). The Linear key is saved with `security add-generic-password -U -s runway-linear`; it is only held in the secure field until saved, is masked in the command shown, is scrubbed from any output, and is never written to a file or log (`security` has no stdin form, so it is briefly in that process's arguments). The steps are a list (`SetupPlan.steps`, `SetupStep`), shown first, then run in order with output streamed: `setup.sh`, `runway setup`, a claim check, `schedule.sh install`. The GitHub tracker swaps the keychain check for `gh auth status` ("Open Terminal to sign in" runs `gh auth login`), takes an optional `owner/name` (blank reads the clone's origin), and runs `setup.sh <repo> --github [owner/name]` then the same `runway setup`, claim check and install. A GitHub project is named by its `github.repo` (else the folder name), and the details pane's ticket button reads "Open in GitHub" there, "Open in Linear" otherwise. A git tracker only installs the schedule. The claim check reads `runway status --json` and warns about tickets stamped by another machine (DAT-11); it never stops the flow. A failed step stops the flow and shows what it printed; every step is safe to repeat, so "Run again" starts from the top. A non-claude harness needs a matching `harnesses` profile in `runway.json` (else the engine falls back to claude), so that step refuses and says so.

Terminal pane (`RunwayCore/Sessions.swift`, `RunwayBar/SessionPane.swift`): **Talk it through** starts its `runway discuss` session in a pane docked at the bottom of the Runway window instead of Terminal.app, one tab per ticket (titled by its id, "loop" for `discuss --loop`, or "last review" for `discuss --review`). SwiftTerm's `LocalProcessTerminalView` runs `/bin/zsh -lc "cd '<repo>' && python3 '<runway.py>' discuss '<id>'"` in a real PTY; the login shell makes PATH, `claude`, `ringer` and `gh` match what the loop sees. That shell line is built by the same function as the Terminal command (`RunwayTools.shellLine`), so the command has one source and the pane is a second launcher for it. Clicking the button on a ticket that already has a live tab focuses that tab; once its process has exited, a click starts a fresh one. Each tab has **Pop out to Terminal** (asks, ends the pane's session, then runs the Terminal command) and a close button that asks first while the process is alive. Quitting with live sessions asks first and says they end with the app, which is the cost against Terminal.app, where sessions outlive it. The setting **Open Claude sessions in** (Runway window / Terminal) is in the menu bar menu; the default is Runway window, and it is stored as `sessionPlace` in the app's defaults, so Terminal is one switch away.

Sign in (`RunwayCore/SignIn.swift`, the top of the side panel and the menu bar menu): when a loop's last sign-in check (`signin.checks` in `status --json`) has a failing tool, or the machine-wide pause carries `"reason": "signed-out"` (the engine paused itself after an agent call failed on auth), the side panel shows a **Needs you · sign in** section above every project, the menu gets "Sign in to <tool>…" and the icon's count and bell include it. One row per tool, however many projects report it. A row shows the command it runs (the check's `fix`, e.g. `claude auth login`); **Sign in** runs that in the window's pane through `/bin/zsh -lc`, always the pane, whatever the session setting, because its exit starts the re-check. When the tab's process exits, the app runs `runway --root <repo> signin --json` in every project; when all pass it runs `runway resume --if-reason signed-out` (a pause Joe set stays) and kicks a tick for each loaded loop that was waiting on a sign-in or paused, then shows "<tool>: signed in. Runway carries on." or what still fails. A check with no `fix` (an older engine) shows a **Recheck** button instead. Pop out to Terminal works for a sign-in tab. The "Set up a loop" sheet still opens Terminal for its sign-ins: the sheet is modal over the window, so the pane behind it can't take typing.

Chores (`RunwayCore/Chores.swift`, the This Mac sheet and each project's menu): the engine checkout's `pm/runway/chores.json` (fields in `pm/runway/chores.md`) lists machine chores as data, so a new one needs no app release. The This Mac sheet's **Chores** section lists the `cwd: checkout` chores whose `show_if` passes (each run through `perl`'s alarm for at most 10 seconds), with `why`, the exact line and folder, and **Run**; a chore marked `confirm` asks once more. Run closes the sheet (it's modal over the pane) and runs the line in the window's pane through `/bin/zsh -lc`. When that tab's process exits, `show_if` runs again and the row says "Done: no longer needed" or that it still looks needed. `cwd: repo` chores (Check tracker setup) are in each project's menu, with the line as the item's help. A missing or unreadable file, or an unknown `version`, hides the list and says why.

## Build, run, test

```bash
cd factory/app
swift build            # debug build
swift test             # RunwayCore unit tests
./make-app.sh          # release build -> build/Runway.app
open build/Runway.app  # menu bar item, no Dock icon (LSUIElement)
bash make-app.sh --install  # build, copy to /Applications/Runway.app and open it
```

`make-app.sh` prints the Login Items steps: System Settings > General > Login Items & Extensions > `+` > pick `build/Runway.app`.

## Check command

`factory/scripts/check.sh` already runs `swift test` in `factory/app` once `Package.swift` exists, so the repo's `runway.json` `check_cmd` (`bash factory/scripts/check.sh`) covers the app. If you use a different `check_cmd`, include `(cd factory/app && swift test)`.

Install with `bash make-app.sh --install` (puts it in `/Applications`). The engine opens it in the background whenever a `tick`, `loop` or `finish` starts and it isn't running (`ensure_app` in `runway.py`; `RUNWAY_NO_APP=1` turns that off).
